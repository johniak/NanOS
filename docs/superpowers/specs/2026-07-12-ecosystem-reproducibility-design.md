# NanOS ecosystem reproducibility — everything forked, tracked, documented

**Date:** 2026-07-12
**Status:** design approved in conversation; this is the written spec for review.
**Goal:** a fresh machine + this document = a fully working NanOS build — kernel, image64,
every port (ping, ifconfig, ssh, browser, sqlite, openssl, vim, htop, git, …), USB/graphics
drivers, the GL desktop stack, and the Dell flash flow. Nothing may live only on one Mac.

## Problem

Today `make image64` + the port targets pull from `~/Projects/nanos-sdk-work`, an
**unversioned build workspace**: extracted upstream tarballs (some modified in place), port
recipes (`nxport.toml`, hooks, build scripts, patches), and two host-side forks (QEMU,
virglrenderer) whose only "history" is loose `*.modified` file copies. Several NanOS-adjacent
projects on this Mac have no remote at all. If this disk dies, large parts of the ecosystem
die with it.

## Design

### Principle

**Home of everything: the `github.com/NanOS-labs` organization** (created 2026-07-12).
**Every upstream thing we modify = its own fork under `NanOS-labs`**, branch `nanos`,
our changes as reviewable commits on top of a pinned upstream base, and **the port recipe
lives inside that fork** (`nxport.toml`, `hooks/`, build scripts, compat headers, Dockerfiles)
— the pattern `vim-nanos` already uses. Where recipe copies have drifted, **the
`nanos-sdk-work` version wins** (it is what actually builds today); after reconciliation the
fork is the single source of truth and `nanos-sdk-work` becomes a disposable checkout area.

### New repos to create (~20)

| Repo | Base | Contents beyond upstream |
|---|---|---|
| `mesa-nanos` | mesa 24.2.8 | 4 patches as commits + all mesa-port build scripts, wrappers, `cross-nanos64.ini`, compat headers, Dockerfiles, `gles2info.c`/`glkms` sources sync-checked against in-tree copies |
| `libdrm-nanos` | libdrm 2.4.123 | 1 patch + `build.sh` + `nanos-compat.h` + `cross-nanos64.ini` |
| `qemu-nanos` | the master snapshot in `qemu.tar.gz` | 3 scanout fixes as commits + `build-qemu.sh` |
| `virglrenderer-nanos` | virglrenderer 1.3.0 | the 20 startergo tap patches **vendored as commits**, the `-drain` experiment as a branch, `build-virgl.sh` |
| `nano-packages` | (own project) | push as-is (28 commits) |
| `sqlite-nanos` | (exists locally) | create GH repo, push |
| `openssl-nanos`, `dropbear-nanos`, `git-nanos`, `htop-nanos`, `wget-nanos`, `zlib-nanos`, `libpng-nanos`, `libjpeg-nanos`, `darkhttpd-nanos`, `inetutils-nanos`, `ncprobe-nanos`, `toybox-nanos`, `sudo-nanos`, `grep-nanos`, `bzip2-nanos`, `busybox-nanos` | respective upstream versions currently in sdk-work | each carries its own recipe (`nxport.toml`/hooks or build script); `inetutils-nanos` carries both recipe dirs (`inetutils-port`, `inetutils-services-port`) |

Migration procedure per repo (mechanical, scripted where possible):
1. Materialize the pristine upstream base (tarball or upstream git tag) as the fork's base.
2. `diff -r` the sdk-work tree against pristine → any in-place modification becomes a commit
   (this audit step guarantees no silent local change is lost — several trees are *believed*
   clean but must be proven so).
3. Add the recipe files as a commit: `nxport.toml` + `hooks/` at the repo root (the
   vim-nanos convention); auxiliary build scripts/Dockerfiles under `nanos/` if they would
   clutter the root.
4. Push to `github.com/NanOS-labs/<name>`, default branch `nanos`, upstream base tagged.

Additionally, the repos that already exist under `github.com/johniak` — `NanOS`, `nanos-sdk`,
`vim-nanos`, `ncurses-nanos`, `bash-nanos`, `netsurf-nanos` — are **transferred into
`NanOS-labs`** (GitHub transfer preserves stars/issues and auto-redirects old URLs; local
remotes and any hardcoded URLs in docs/scripts get updated afterwards).

### Rescues into the main NanOS repo

- `nanoos-ui` mockup: unzip `~/Downloads/nanoos-ui(1).zip` → `docs/design/nanoos-ui/`, commit.
- Commit the untracked plan/design docs listed in finding 8 (curate: build artifacts like
  `disk/image64-grub2.img` stay out; `scratch/` stays untracked as working space).

### Bootstrap: fresh machine → working everything

`bootstrap.sh` in the `nanos-sdk` repo (the entry point a new machine clones first):

1. **Host prerequisites check**: Docker, brew packages (qemu, e2fsprogs, python3 + Pillow,
   startergo taps for angle/libepoxy with pinned versions), git, ssh keys.
2. **Clone all forks** into today's `nanos-sdk-work/` directory layout
   (`mesa-port/mesa-24.2.8`, `vim/`, `toybox-0.8.11/`, …) so **no NanOS Makefile path
   changes are needed** on day one. A manifest file (repo → checkout path → pinned ref)
   drives this; the manifest is the machine-readable half of the ecosystem docs.
3. **Build the toolchain** (i686 + x86_64) and the two Docker images (`nanos-build` from
   NanOS `docker/`, `nanos-sdk-dev` from nanos-sdk).
4. **Build all ports in dependency order**: zlib → openssl → {wget, dropbear}; ncurses →
   {vim, htop}; libpng/libjpeg → netsurf; libdrm → mesa → {gles2info, glkms, nwm-gl};
   plain ports (toybox, sudo, grep, bzip2, busybox, git, sqlite, bash, darkhttpd, inetutils,
   ncprobe) as available.
5. **Build the host GL stack**: virglrenderer-nanos dylib, qemu-nanos binary (macOS only;
   skippable — only needed for `run64-gl*`).
6. `make image64` (+ optionally `make externals && make image64` re-run to fold staged apps in).

Every step is idempotent — a half-finished bootstrap resumes where it stopped.

### Documentation deliverable (in the main NanOS repo)

`docs/ECOSYSTEM.md`:
- **Repo table**: every repo (main + all forks), upstream base, what we changed and why, which
  Makefile target consumes it, where bootstrap checks it out.
- **Dependency graph** of ports (the build order above, as a diagram).
- **Fresh-machine walkthrough**: from `git clone nanos-sdk && ./bootstrap.sh` to a booting
  `image64` in QEMU and a flashed Dell stick, including the host GL stack for `run64-gl`.
- **Host dependency list with versions** (brew formulas, taps, Docker, QEMU).
- README gets a short "Ecosystem & reproducibility" section linking to it.

### Verification gate

The step-zero work is DONE only when a clean-room bootstrap passes:
`SDK_WORK=/tmp/fresh-sdk-work bootstrap.sh` on this Mac (and ideally once on a second
machine) must produce an `image64` whose booted system has ping, ifconfig, telnet, ssh
(dropbear), openssl, sqlite3, vim, htop, git, bash, netsurf, toybox login, sudo — plus a
built `nwm-gl.nxe` and the host virgl QEMU able to run `run64-gl-desktop`. The existing
`verify64` suite must stay green throughout.

### Out of scope (follow-up project)

**Build unification** — one `image64` with the GL-capable nwm (runtime CPU fallback) as the
only compositor, i915 auto-arm on hardware detection, single `run64` / `flash-dell`. This was
the original request; it becomes safe to hard-depend `image64` on Mesa only once mesa-nanos
exists. Separate spec/plan after step zero lands.

## Relation to the existing "buildable from scratch" plan chain

The 2026-07-02 spec (`2026-07-02-buildable-from-scratch-design.md`) and its plans
(`2026-07-02-plan-1-repo-reorg-manifest-bootstrap`, `2026-07-02-plan-2-make-world-building-docs`,
`2026-07-04-gl-userspace-refactor`, `2026-07-04-host-reproducibility-macos-ubuntu`) attack the
same reproducibility problem. **This spec supersedes their answer to "where do port recipes
live":** Plan 1 put recipes in `nanos-sdk/ports/<name>/` with a `nanos-fetch` materializer,
and the GL-refactor plan rescued mesa recipes into `ports/mesa-gl/`; the decision now is
**per-upstream forks carrying their own recipes** (this document). Everything else in that
chain remains valid and complementary — `make world`, BUILDING.md, the build server / CI
plans, the Ubuntu host story — and `bootstrap.sh` + the manifest described here fill the same
role Plan 1's manifest did, just pointing at forks instead of an in-sdk ports tree. The plans
index (`docs/superpowers/plans/README.md`) must be updated to reflect this supersession.

## Risks / notes

- `qemu-src` has no git history; the fork base is reconstructed from `qemu.tar.gz`. If the
  tarball doesn't match a public QEMU commit exactly, the base is committed as-is and tagged
  (provenance noted in the commit message) — correctness of the diff matters more than a
  pretty ancestry.
- The startergo angle/libepoxy **host dylibs** remain brew-tap dependencies (we don't fork
  ANGLE); pin + document versions, and note the re-sign quirk (`codesign --force`) already
  encoded in the Makefile.
- GitHub "fork" objects vs plain repos: mesa/libdrm/virglrenderer upstreams live on
  freedesktop GitLab; those become plain repos initialized from the pinned upstream, which
  satisfies the tracking requirement identically.
- `server/db.sqlite3` and other runtime artifacts in nano-packages should be gitignored
  before the push, not committed.
