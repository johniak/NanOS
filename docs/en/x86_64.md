# NanOS on x86_64 (64-bit long mode)

NanOS started life as a 32-bit i686 kernel. It was **migrated to x86_64 (long mode) as a
replacement, not a second architecture** — there is no pre-x64 CPU support kept alive. x86_64 is
the sole development target; i686 is **frozen** (kept only as a build-able reference / debugging
oracle, never extended — decision 2026-06-19). This doc covers what is x86_64-specific: the
long-mode boot trampoline, 4-level paging, the LAPIC/MSI interrupt path, the in-kernel USB stack,
the build/run flow, and the real-hardware boot. Everything *above* the arch boundary (the VFS,
scheduler, syscalls, net stack, NanWM) is machine-independent and documented in its own per-subsystem
doc; this one is the machine-dependent (MD) layer for x86_64.

> **Status honesty.** Throughout, claims are tagged **[QEMU]** (verified headless in QEMU),
> **[HW]** (verified on the real Dell Latitude 5310), or **[open]** (designed/known but not yet
> done or not yet verified).

```
Limine ──multiboot1──► loader.S (0x100000, 32-bit PM) ──► long-mode trampoline ──► kentry64(rdi=mb)
  BIOS or UEFI            build temp 64 GiB identity map      PAE + EFER.LME + CR0.PG          │
  on hybrid GPT           load 64-bit GDT (L=1), far-jump     → 64-bit code segment            ▼
                                                                                       kmain() → Kernel::start()
                                                                                       (shared MI bring-up, boot.md §4)
```

---

## 1. Why 64-bit-first, as a replacement

The MI/MD split (`arch/include/arch/` contracts + `arch/<arch>/` implementations, selected by
`ARCH`) is what made a *replacement* feasible: adding `arch/x86_64/` is a new implementation of the
same contracts, not a kernel rewrite. Going 64-bit-first (rather than 32-bit with PAE, or a compat
userland) buys:

- **NX / W^X** — the page-table No-Execute bit (PTE bit 63) is always available; the kernel enables
  `EFER.NXE` and honours NX on user mappings.
- **>4 GiB RAM** — physical addresses and the page tables are 64-bit, so the machine can use memory
  above the 4 GiB PCI hole. **[QEMU]** `make smoke-bigmem` boots with 6 GiB.
- **One ABI, one toolchain** — native x86_64 userland (SysV AMD64), the `syscall`/`sysret` fast
  path, and a single `x86_64-elf` / `x86_64-nanos` toolchain instead of i386 + a compat shim.
- **APIC / UEFI assume 64-bit** — the LAPIC, MSI, and real UEFI firmware are the modern baseline the
  hardware target (a UEFI laptop) requires.

The cost is a one-time rebuild of the userland ecosystem against an `x86_64-nanos` SDK — paid once,
not maintained as a second variant. The full pre-migration analysis is
`docs/superpowers/specs/2026-06-15-x86_64-migration-analysis.md`; the honest post-migration status is
`docs/superpowers/specs/2026-06-19-x86_64-honest-status-and-gap-analysis.md`.

## 2. The MI/MD split, preserved

`arch/x86_64/` implements exactly the `<arch/...>` contracts in `arch/include/arch/`
(`mmu.h`, `cpu.h`, `irq.h`, `syscall.h`, `usermode.h`, `sched.h`, `bootinfo.h`, `block.h`,
`usbhc.h`, …). The MI code (`init/ kernel/ mm/ fs/ lib/ drivers/ usb/ net/`) reaches hardware
**only** through those headers, never through x86_64 internals.

- `arch/x86_64/arch.mk` supplies the MD build knobs: `CROSS = x86_64-elf-`, `ASM_FMT = elf64`,
  `QEMU = qemu-system-x86_64`, `QEMU_CPU = -cpu qemu64`, the kernel codegen flags
  `KARCHFLAGS = -mno-red-zone -mno-sse -mno-mmx -mno-80387` (the kernel must never touch XMM across
  an interrupt, and interrupt handlers must not clobber the red zone), and `ARCH_SOURCES` (the MD
  object list — loader, entry, GDT/IDT, interrupt path, paging, drivers, LAPIC, xHCI).
- The 64-suffixed basenames (`Gdt64.o`, `Idt64.o`, `isr64.o`, `switch64.o`, …) avoid colliding with
  i686's same-named objects in `bin/`.
- **`make check-arch`** still greps the MI dirs and fails if any x86 internal (`Registers`, port I/O,
  inline asm, MD headers) leaks back in — run it after MI edits. The guard is arch-neutral.

The `ARCH` switch is kept (cheap, and the natural hook for a future ARM port); `arch/x86` remains in
the tree as the frozen reference. `ARCH ?= x86` is still the *default* — x86_64 targets pass
`ARCH=x86_64` (or are pinned independent of `ARCH`, see §7).

## 3. Boot in long mode

Contrast with the i686 path (boot.md): there, GRUB2 hands a 32-bit Multiboot kernel to a tiny
`loader.s` that just sets `esp` and calls `kmain`. On x86_64 two things change — the **bootloader**
(Limine, for dual BIOS+UEFI boot) and the **long-mode trampoline** the loader must run before
`kmain`.

### 3.1. Bootloader: Limine on a hybrid GPT image

The x86_64 disk image (`disk/image64-grub2.img`, built by `make image64` → `_image64` →
`scripts/create-grub2-image.sh` with `NANOS_BOOT=limine`) is a **hybrid GPT** image bootable under
**both legacy BIOS and UEFI** via **Limine 8.7.0**:

```
GPT:  P1 bios_boot (1 MiB)   P2 ESP / FAT32 (64 MiB)              P3 ext2 root  (label NANOS)
      Limine BIOS stages     BOOTX64.EFI + limine-bios.sys        /nanos/core/kernel.bin
      (limine bios-install)  + limine.conf (protocol: multiboot1)  + the on-disk tree
```

- The kernel itself is **unchanged Multiboot1** — Limine's multiboot1 loader (BIOS *or* UEFI) reads
  `kernel.bin` off the root by `fslabel(NANOS)` and hands off in 32-bit protected mode, exactly as
  GRUB did. The trampoline (§3.2) does the rest.
- **The root is ext2, not ext4** — Limine's ext4 reader panics on the extent tree, so the root is
  block-mapped ext2 (which the kernel auto-detects and mounts read-write). Trade-off: ext2 has no
  JBD2 journal. (ext4+JBD2 is still used for the `-drive`/USB QEMU images.)
- The ESP **must be FAT32** (not FAT16): real UEFI firmware rejects a FAT16 ESP (OVMF tolerated it).

The i686 GRUB2/MBR image path (`make image`/`run`) is untouched and still builds — it is gated by
the default `NANOS_BOOT`.

### 3.2. The long-mode trampoline (`arch/x86_64/boot/loader.S`, NASM, elf64)

Limine enters `loader` in **32-bit protected mode** at `0x100000` (the Multiboot header is in
`.multiboot`, placed first by `arch/x86_64/linker.ld`, `OUTPUT_FORMAT(elf64-x86-64)`). The
multiboot info pointer arrives in `ebx`. The trampoline then:

1. sets `esp` to a **1 MiB** boot stack (raised from 16 KiB — the MI ext driver's mount/read paths
   recurse with 4 KiB block buffers, and 64-bit frames are larger, so it overflowed into `.data`);
2. `mov edi, ebx` — stash the multiboot pointer so it becomes `rdi` (arg0) in long mode;
3. **builds a temporary identity map** — a PML4 → one PDPT → **64 contiguous PDs** filled with
   2 MiB huge pages, identity-mapping **[0, 64 GiB)**. (The first cut mapped only 1 GiB; on real
   8–16 GiB hardware the Multiboot info / E820 map / framebuffer sit higher, and a pre-paging access
   to them triple-faulted with no output — **[HW]** fix);
4. enables paging into long mode: `CR3 = PML4`, `CR4.PAE`, `EFER.LME` (MSR `0xC0000080` bit 8),
   `CR0.PG` — at which point long mode activates;
5. `lgdt` a minimal 64-bit GDT whose code descriptor has the **`L` (long-mode) bit** set, then
   `jmp gdt64.code:long_mode_start` — the far jump that loads a 64-bit `cs`;
6. in 64-bit code, nulls the data segment registers, sets `rsp`, and `call kentry64` (`rdi` already
   holds the multiboot pointer).

`kentry64` (`arch/x86_64/boot/entry64.cpp`) stashes the pointer for the bootinfo layer
(`bootinfo_x86_64.cpp` parses the mmap + framebuffer, like the i686 `bootinfo_x86.cpp`) and calls
the MI `kmain()`. From there `Kernel::start` is the **shared, ordered bring-up** described in
boot.md §4 — `cpuInit` (GDT/IDT/TSS, §5), `initPaging` (§4), storage, devices, kexts, syscalls,
scheduler — none of it x86_64-specific beyond the contracts it calls. **[QEMU]** boots to a
`bash-5.2#` prompt on the framebuffer console.

## 4. 4-level paging (PML4)

i686 used 2-level paging (10|10|12). x86_64 uses **4 levels** of 512 eight-byte entries
(`arch/x86_64/mm/Paging.h`):

```
canonical VA (bits 48..63 sign-extend bit 47)
 │
 ├─[63]  NX (No-Execute, honoured when EFER.NXE=1)
 │
 │   47        39 38        30 29        21 20        12 11            0
 ▼   ┌───────────┬────────────┬────────────┬────────────┬──────────────┐
 VA: │ PML4 (9)  │ PDPT (9)   │ PD (9)     │ PT (9)     │ offset (12)  │
     └─────┬─────┴──────┬─────┴──────┬─────┴──────┬─────┴──────────────┘
           ▼            ▼            ▼            ▼
        PML4[i] ───►  PDPT[i] ───► PD[i] ─────► PT[i] ──► 4 KiB frame
                                    │
                                    └─ PS=1 (bit 7): PD entry maps a 2 MiB huge page (no PT)
```

Frame address is bits 12..51 (`PAGE_MASK`); the low 12 bits are the control flags
(`PTE_PRESENT/RW/USER/PS`), bit 9 is the software-only `PTE_PRIV` marker (see below), and bit 63 is
`PTE_NX`. `Paging.h` also provides `canonical()`/`isCanonical()` — VAs must sign-extend bit 47.

### 4.1. Kernel bring-up (`arch/x86_64/mm/mmu_x86_64.cpp`, implements `<arch/mmu.h>`)

`mmuInitKernel(frames, topOfRam)`:

1. re-reserves the regions the frame pool must never hand out (low mem + VGA, the kernel image, the
   exec-staging window at `VA_USER_BASE`);
2. lays the kernel heap — carved as ~25% of RAM clamped to [8 MiB, 256 MiB], placed within the
   **first 1 GiB** (it is first-touched while only the loader's temporary map is live, before CR3 is
   switched);
3. builds a fresh PML4 and **identity-maps all RAM with 2 MiB huge pages** (`mapRangeHuge`) — cheap
   for many GiB;
4. `cli`, `enableNxe()`, `loadCr3(kernelDirPhys)` (off the loader's temporary map onto our PML4),
   `enablePaging()` (re-assert CR0.PG), `sti`;
5. maps the LAPIC MMIO page and brings up the Local APIC (§5).

### 4.2. The >1 GiB ceiling fix and the MMIO-overlap guard

Two related issues, both surfaced only above ~1 GiB (QEMU's small RAM hid them):

- **>1 GiB RAM / >4 GiB usage** — identity-mapping *all* of RAM with 2 MiB huge pages (step 3, plus
  the loader's 64 GiB temporary map) lets the kernel boot and run with large memory. **[QEMU]**
  `make smoke-bigmem` (-m 6144) exercises a usable region above the 4 GiB PCI hole.
- **MMIO on a live huge page** — once *all* RAM is huge-mapped, device MMIO (the LAPIC at
  `0xFEE00000`, the framebuffer) may fall **inside** the huge identity map on a big-RAM machine.
  Re-mapping it with a 4 KiB `mapRange` would walk the live 2 MiB huge PDE as if it were a
  page-table pointer → corruption → triple fault. The `g_identityTop` guard skips re-mapping
  anything already covered by the huge map; only MMIO *above* it (the QEMU case) gets an explicit
  4 KiB mapping. **[HW]** This was the fault that stopped boot right after the white POST bar on the
  Dell (16 GiB).

### 4.3. Per-process address spaces (`arch/x86_64/mm/AddressSpace.*`)

Each process gets its own PML4 that **shares the whole kernel half** (so syscalls/IRQs run with the
kernel mapped under any CR3) and owns **private** page tables for each user window:

- `mmuCreateAddressSpace()` → `adoptKernelDirectory(kernelDir, VA_USER_BASE)` copies the kernel
  PML4 entries, then `dropUserWindows()` privatizes every user-window PD entry. This is the
  **per-process window privatization** that keeps the >1 GiB kernel identity map (which lives in the
  shared half's `pdpt[1]`) from leaking its huge entries into a process's user windows.
- **`PTE_PRIV` (AVL bit 9)** marks an entry as pointing at a per-process private table, making
  privatization **idempotent** and letting teardown free exactly the private intermediate tables.
  This fixed a leak where `privatizeChild` re-allocated already-private tables (~27/fork) and
  teardown never freed them — **~232 KB leaked per process**; re-measured **flat** after the fix
  (650 alloc == 650 free). **[QEMU]**
- `mmuCopyAddressSpace` (fork, eager copy of each populated window), `mmuFreeAddressSpace` (frees the
  private leaf frames + private intermediate tables + PML4, leaves the shared kernel half),
  `mmuSetUserBrk`/`mmuMapAnon` (grow brk/mmap by mapping fresh zeroed `USER|RW` frames — done under
  the kernel CR3, the only place a fresh frame is identity-accessible to zero).
- `AddressSpace` is pure logic → **host-tested** (`tests/test_addressspace64.cpp`,
  `tests/test_paging64.cpp`, run by `make test64`).

The user VA windows (`arch/include/arch/mmu.h`) are deliberately kept in the low canonical range —
small-code-model / non-PIC `.nxe`s load there:

| Window | VA range | Note |
|---|---|---|
| program image + 512 KiB stack | `0x00800000` – `0x04000000` | `VA_USER_BASE` … `VA_USER_END` (64 MiB) |
| `.ndl` module band | `0x40000000` – `0x48000000` | 1 GiB base, 4 MiB stride, 32 slots |
| heap / `brk` | `0x48000000` – `0x4C000000` | 64 MiB |
| `mmap` | `0x50000000` – `0x54000000` | 64 MiB |
| user framebuffer | `0x58000000` – `0x5C000000` | MMIO, mapped on demand |

> **[open]** A single-process user window larger than ~1 GiB is *not* exercised — the windows above
> are each modest (≤64 MiB). The documented VA-window ceiling is the gate before any large-RAM /
> heavy-multiprocess workload that needs a huge per-process window. See
> docs/superpowers (paging carry-forward).

For the MI side of memory (frame allocator, kernel heap, `/proc/meminfo`), see memory.md — those
modules are shared; only this MD layer changed for 64-bit. (`FrameAllocator` is still 32-bit-physical;
the `mmu_x86_64` wrappers widen its `uint32_t` to the `uint64_t` the page tables want — lossless for
RAM ≤ 4 GiB; a >4 GiB-aware allocator is a planned cleanup.)

## 5. Interrupts, the GDT/IDT, the LAPIC and MSI

`arch::cpuInit()` (`cpu_x86_64.cpp`) installs the 64-bit GDT (`Gdt64.*`) + TSS (`Tss64.h`, 64-bit
TSS with `rsp0`/`ist1..7`) and the IDT (`Idt64.*`), then the keyboard. The structures differ from
i686:

- **64-bit IDT gates** are 16 bytes: a 64-bit handler split `base_lo/mid/hi`, plus a 3-bit **IST**
  index. `Idt64::initialize` sets all 256 gates, remaps the 8259 PIC to `0x20`/`0x28` (same as
  i686), and routes **#DF (vector 8) to IST1** — a dedicated known-good stack so a corrupt `rsp`
  cannot cascade to a triple fault.
- The interrupt entry/exit path is hand-written (no `pusha`/`popa` in long mode): `isr64.S`/`irq64.S`
  push/pop the 15 GPRs, `swapgs` on the user/kernel boundary, and `iretq`; the `Registers`
  trap-frame is the x86_64 GPR set. The IRQ-return path wires the ring-3 **preemption**,
  **fault → kill**, and **signal-delivery** hooks (all three were Plan-1..4 debug stubs initially;
  fixed to mirror i686).
- **Syscalls use `SYSCALL`/`SYSRET`** (not `int 0x80`): `syscallInit` (`syscall_x86_64.cpp`)
  programs `EFER.SCE`, `STAR`, `LSTAR` (→ `syscall_entry`), `FMASK`, and `KERNEL_GS_BASE`; the stub
  `swapgs`es to a per-CPU block, builds a `Registers` frame, and dispatches with the AMD64 SysV
  convention (nr in `rax`, args `rdi/rsi/rdx/r10/r8/r9`) into the MI `kernelSyscall`. Userland
  uses the **x86_64 Linux syscall numbers**, and the per-task **`%fs.base`** (picolibc's thread
  pointer for `errno`/stdio) is reloaded on every context switch.

### Local APIC + MSI (`arch/x86_64/cpu/lapic_x86_64.*`)

A **minimal** Local APIC, brought up from the tail of `mmuInitKernel` — **not** from `cpuInit` —
because it needs its MMIO register page mapped first, and a late page-table allocation at `cpuInit`
time would corrupt the live kernel stack. `lapicInit()`:

- sets the global-enable bit in `IA32_APIC_BASE` and the spurious-interrupt vector (`0xFF`);
- initializes a tiny **MSI vector pool** (`msiVecAlloc`, pure logic, host-tested) handing out
  vectors `0x70..0x77`, gated in the IDT to the `irq_msiN` stubs and EOI'd via the LAPIC (not the
  PIC).

This is **single-vector MSI** — one interrupt vector per device, *not* multi-queue MSI-X. It is what
the modern NIC drivers (e1000e / I219, see networking.md) use: a single MSI for a single RX/TX queue.
**[QEMU]** `make smoke-e1000e` boots with the 82574L (`-device e1000e`) to exercise the LAPIC + MSI
path headless. The I219 (ich9lan) kext is real-HW-only and a no-op under QEMU — **[open]** untested
until the Dell.

### 5.2. SMP / multicore (`arch/x86_64/cpu/smp_x86_64.cpp`, `<arch/smp.h>`)

NanOS runs on up to `SMP_MAX_CPUS` (32) logical CPUs. The MD code lives behind `<arch/smp.h>`; the
i686 build keeps a uniprocessor stub so it still links.

- **CPU enumeration** — `kernel::Acpi` (MI, host-tested) parses the ACPI RSDP/RSDT/XSDT + **MADT**
  for the application-processor LAPIC ids; `acpi_x86_64.cpp` finds the RSDP (EBDA + `0xE0000..0xFFFFF`).
- **AP bring-up** — `ap_trampoline.S` is copied to a fixed low page (`0x8000`); the BSP sends
  **INIT–SIPI–SIPI** per AP (Intel SDM §8.4) and spins until each marks itself online. Each AP enters
  long mode on the BSP's kernel PML4, sets up its **per-CPU block** (GS-indexed; both GS bases written
  in `perCpuInitThis`, *after* the per-CPU GDT load that zeroes the hidden GS base — a swapgs-parity
  bug fixed in Phase 3), its own GDT/TSS, and a **per-CPU LAPIC timer**, then drops into its own idle
  task. `smpThisCpu()` reads the LAPIC id (GS-independent, correct in every context).
- **Scheduling** — `g_curTask`/`g_needResched`/`g_slice` are per-CPU; the shared runqueue is the
  global `g_tasks[]`. The BSP's PIT owns global timekeeping (`g_ticks`, timed wakeups, load average);
  each AP's LAPIC timer drives only its own quantum. The context-switch handoff keeps a `runningCpu`
  gate so a task woken before its outgoing CPU has saved its kernel `rsp` is not claimed by a second
  CPU (the wake-during-switch-out fix).

**Locking — Big Kernel Lock → fine-grained (Phase 4).** Phase 3 brought correctness up by
serialization: a single recursive **BKL** wrapped every kernel episode (the syscall/IRQ/fault entry
stubs + the scheduler handoff) while per-subsystem locks were layered in underneath. Phase 4 then
**retired the BKL** once every shared structure had its own lock:

- `kernel/Spinlock.h` — a ticket `Spinlock` + guards: `SpinGuard`/`SpinIrqGuard` and a per-CPU-keyed
  `RecursiveSpinlock` with `RecursiveGuard`/`RecursiveIrqGuard` (lets a subsystem's composing methods
  re-enter on the same CPU instead of self-deadlocking). The acquire-spin polls
  `arch::smpPollShootdown()` so a CPU spinning with interrupts off still services a TLB shootdown.
- Per-subsystem locks: runqueue (`g_rqLock`, released across the context switch), process table
  (`g_procLock`), VFS + block cache + JBD2, frame allocator + heap, the per-process fd table, pipes,
  the futex table, the exec staging window (`g_execLock`), the console, and a coarse network-stack
  lock (`g_netLock`). Global lock order: `m_fdLock → g_netLock → g_rqLock`, `g_procLock → g_rqLock`.
- **TLB shootdown** — `smpTlbShootdown()` IPIs the other CPUs (a per-CPU mailbox + ack count) and
  spins until each flushes its CR3; targets service it from the IPI handler *or* from the spinlock
  poll above, so it never deadlocks against a CPU that holds a lock with interrupts disabled. Wired
  into the user unmap/free paths (unmap → shootdown → free, so no CPU keeps a stale entry to a reused
  frame).

**[QEMU]** SMP is gated under **MTTCG** (`-accel tcg,thread=multi`, required — single-threaded TCG
round-robins all vCPUs on one host thread, so no parallelism is observable):
- `make smoke-smp` — 4 vCPUs come online + reach login (scheduler healthy);
- `make smoke-smp-speedup` — `user/pfract` runs the same fixed job on 1 then 4 threads and asserts a
  real speedup with an identical checksum (≈3–4×);
- `make smoke-smp-stress` (`user/smptorture`) + `make smoke-smp-netstress` (`user/nettorture`) — the
  **data-race gates**: many threads hammer the fd table, a shared pipe, signals, a mutex counter, and
  UDP-over-loopback (driving the RX-softirq thread), with deterministic order-independent oracles, so
  a missed lock would corrupt an oracle. All are wired into `make verify64`.

**[open]** Real-HW SMP is untested until the Dell (QEMU `-smp` is the gate; Limine's ACPI provides the
same MADT path). Per-process address spaces are active on one CPU at a time, so cross-CPU shootdown is
the rare multithreaded-munmap case; signal-mask and job-control updates rely on single-word (`uint64`)
atomicity rather than a dedicated lock (a documented follow-up).

## 5.3. Virtual terminals (`Ctrl+Alt+Fn`) (`kernel/vt/`, `drivers/VtTty.*`)

Like Linux, NanOS multiplexes the **physical console** (keyboard + framebuffer) into several virtual
terminals, switched with `Ctrl+Alt+Fn`:

- **tty1–tty6** are kernel **fbcon** text consoles (the `FbConsole`/`vt.c` engine). `init` runs a
  getty/login on each (`setsid` + `TIOCSCTTY` on `/dev/ttyN`), so each is an independent login
  session. The active console after boot is tty1.
- **tty7** is the **graphics** console: the window manager `nwm` owns it via the Linux
  `KDSETMODE(KD_GRAPHICS)` + `VT_SETMODE(VT_PROCESS)` protocol.

**Kernel pieces.** `kernel/vt/VtConsole` is one console — its own line discipline, raw ring, wait
queue, termios, foreground process group, an `FbConsole` with a `live` bit (an off-screen console
keeps its grid but does not blit), and the `KD`/`VT_SETMODE` state. `kernel/vt/VtManager` owns
`vt[1..7]`, the active index, and the real framebuffer, and serializes **all** framebuffer output +
switching under one recursive IRQ lock (the role the single `g_consoleLock` used to play).
`drivers/VtTty` is the `/dev/ttyN` CharDevice; `/dev/tty0` is the active VT, `/dev/tty` the caller's
controlling VT (`Process::cttyVt`, set by `TIOCSCTTY`), `/dev/console` is tty1.

**Switching.** The PS/2 input layer (`input_x86_64.cpp`) matches `Ctrl+Alt+F1..F7` ahead of the
normal decode and consumes it; everything else routes by the active console's mode — a graphics VT
feeds `/dev/input0` (evdev) for its owner, a text VT runs the per-VT line discipline. A text switch
flips the `live` bits and repaints the new console's grid (cheap; the screen state is preserved and
restored exactly). Switching **away from** a process-mode graphics VT sends the owner its release
signal and completes only when it acks with `VT_RELDISP` (or a deadline elapses); switching **to** one
sends its acquire signal so it redraws. The kernel printk/boot console is tty1; a kernel fault
force-switches to tty1 so the panic is visible even over a graphics VT.

**[QEMU]** `make smoke-vt` is the gate: boot, log in on tty1, drive `sendkey ctrl-alt-f2`/`f1` via the
monitor, and assert (byte-exact screendumps) that tty2 differs from tty1 and that the round-trip
restores tty1.

**[open]** `/dev/ttyN` is mode `0666` (the `/dev` SynthFs has no per-node `chown`, so a permissive
mode replaces Linux's chown-tty-to-user-at-login); a unified `/dev/tty` resolution across VT and PTY
controlling terminals is a follow-up.

## 6. The in-kernel USB stack

A complete USB stack lives **in the kernel** (not as a kext), enabling the live-USB scenario (the
whole system on a pendrive, USB as the root device):

```
usb/UsbCore  (enumeration, descriptors)   ─┐
usb/UsbHid   (boot kbd/mouse → scancodes)  ├─ MI core, host-tested via a mock HC
usb/UsbMsc   (BOT + SCSI READ/WRITE(10))   ─┘   (tests/usb_mock_hc.h)
        │
        ▼ <arch/usbhc.h>  (UsbSetup/UsbTransfer/UsbHcOps; usbHostInit)
arch/x86_64/drivers/xhci_x86_64.cpp  — full xHCI host controller:
   PCI discovery (class 0C/03/30), MMIO, command+event rings + ERST, port reset,
   Enable Slot / Address Device, EP0 control + bulk/interrupt endpoints. Poll model (no IRQ).
        │
        ├─ UsbMscBlockDevice  → a BlockDevice (drivers/), mountable as the ext root
        └─ kernel/UsbHidInput.cpp → /dev/input0 (kbd) + a MouseDevice, via a poll kernel thread
```

- **[QEMU]** `make smoke-usb` boots with the entire root filesystem on a `usb-storage` device (no
  `-drive` disk): the in-kernel xHCI + USB-core + MSC path mounts root, the shell comes up, and a
  console fork/exec is typed **through the USB keyboard**. WRITE(10) is e2fsck-clean and a marker
  persists across reboot.
- **[HW]** On the Dell, two real-xHCI fixes were needed (no-ops under QEMU): a BIOS/SMM handoff (USB
  Legacy Support OS-ownership claim + SMI silence, plus guarded Intel port routing), and **Port
  Power** must be asserted + a connect debounce polled before enumeration (QEMU powers ports
  instantly). USB-MSC multi-sector reads return only the first sector on real hardware, so
  `UsbMscBlockDevice` issues **one READ(10)/WRITE(10) per sector** (mirrors the old ATA
  multi-sector-desync fix). A proper multi-TRB bulk path is a perf follow-up.

The legacy ATA path (`ATA64.S`, `AtaBlockDevice64`) is retained as the `-drive` disk fallback.

## 7. Building and running

| Command | What |
|---|---|
| `make image64` | build the x86_64 kernel + 64-bit userland (`init.nxe` etc.) + kexts, install into `disk/image64-grub2.img` (hybrid GPT + Limine). Runs in the `nanos-build` Docker container. |
| `make run64` | `image64`, then boot natively: `qemu-system-x86_64 -cpu qemu64 -m … -drive file=disk/image64-grub2.img,format=raw` + the NIC/NAT/hostfwd net. |
| `make bringup64` | minimal Plan-1 long-mode rescue ISO (proof-of-life). |
| `make test64` | host doctest suite for `ARCH=x86_64` — the MI tests **plus** the 64-bit paging/AddressSpace tests (`test_paging64`, `test_addressspace64`). |
| `make smoke-x86_64` | headless QEMU boot smoke (BIOS/SeaBIOS): asserts long-mode, paging, ATA+ext4 JBD2 write, e1000/net, scheduler, ring-3 fork/exec, **zero faults**. |
| `make smoke-uefi` | the same image under edk2/OVMF (UEFI) → `BOOTX64.EFI` → Limine → kernel. |
| `make smoke-usb` | live-USB boot (root on `usb-storage`, in-kernel xHCI). |
| `make smoke-bigmem` | boot with 6 GiB RAM (a region above the 4 GiB PCI hole). |
| `make smoke-e1000e` | boot with the 82574L (`-device e1000e`) — LAPIC + MSI. |
| `make verify64` | **the full gate**: `test64` + BIOS + UEFI + big-RAM + e1000e + live-USB smokes. |

Notes:

- `QEMU64`/`QEMU_CPU64` (`qemu-system-x86_64 -cpu qemu64`) are pinned **independent of `ARCH`** in
  the Makefile: `run64`/`bringup64` are inherently 64-bit but usually invoked as plain `make run64`
  (no `ARCH=x86_64`), so without the pin they would resolve to `qemu-system-i386`, load the 64-bit
  kernel, fault entering long mode, and reboot-loop. (This was a real bug — fixed.)
- The **memory map is RAM-agnostic** (the heap is a fraction of RAM; identity-mapping is by huge
  pages over `topOfRam`), so the same image boots from 512 MiB up to many GiB.
- Verification model carried over from i686 (CLAUDE.md): **host doctests** for MI logic + **headless
  QEMU** (screendump / `/proc` dump / `-d int` fault scan) for the MD path. The MD layer
  (context switch, fork, SYSCALL entry, paging impl, the kexts) has *no* automated host coverage —
  the `smoke-*` targets are its gate. (The TCP-on-x86_64 bug in §8 is the cautionary tale: host TCP
  doctests passed while real x86_64 TCP was broken.)
- Switching `ARCH` reuses `bin/` for userland objects — run `make clean` when crossing arches.

## 8. Real hardware and open items

**[HW] NanOS boots on a real Dell Latitude 5310** (UEFI Class 3, Comet Lake, NVMe + xHCI) from a USB
stick, all the way `USB → Limine (UEFI) → kernel → init → shell`. Getting there fixed **five
real-HW-only bugs** that QEMU/OVMF had hidden:

1. **FAT32 ESP** — the firmware silently reset on a FAT16 ESP (OVMF tolerated it); the ESP is now
   64 MiB FAT32.
2. **64 GiB loader identity map** — the temporary map was 1 GiB; the Multiboot info / E820 /
   framebuffer sit higher on a big-RAM machine (§3.2).
3. **64-bit MMIO physical addresses** — the framebuffer/BAR phys path was `uint32_t`; real LFB/BARs
   sit above 4 GiB.
4. **The huge-page / 4 KiB-MMIO overlap guard** (`g_identityTop`, §4.2).
5. **Per-sector USB-MSC reads + xHCI port power** (§6).

**Verified working** (mix of [QEMU] and the [HW] boot): kernel boot + 4-level paging + framebuffer
console, `init` → login shell, bash interactive with **fork + pipes**, coreutils + `free`, the
`.nxe`/`.ndl` loader, ext read+write, the interval timer, vim (with ext write), Doom (graphical),
NetSurf + the NanWM desktop, the openssl binary's local crypto, and outbound ICMP (`ping`). USB live
root and USB-HID kbd/mouse are [QEMU]-verified.

**Open / known gaps:**

- **TCP** was the headline x86_64-specific bug. It is **fixed** — two independent root causes: a
  `lookup()` that matched a dead `TCP_CLOSED` TCB ahead of the listener (a reused-4-tuple zombie
  shadow), and a userland↔kernel **SIGCHLD number mismatch** (kernel 17 / picolibc 20) that left
  reaper-armed daemons with un-delivered child-death signals. Both committed + host-tested (120
  back-to-back SSH handshakes complete). **[open]** A `dropbear ssh host cmd` teardown linger remains
  (the command's shell becomes a transient zombie spinning on a never-EOF pipe; contained by
  preemption, not catastrophic).
- **NVMe** — the Dell currently boots from USB; its real NVMe disk is not yet a driver. **[open]**
- **I219 NIC on metal** — the kext exists and is a QEMU no-op; untested on the Dell. **[open]**
- **Native display resolution** — boots at the 1024×768 GOP mode; the panel's native resolution,
  battery/ACPI, and suspend are future work. **[open]**
- **>1 GiB single-process user-VA window** (§4.3) and a **>4 GiB-aware frame allocator** (§4) — both
  documented, not yet exercised. **[open]**
- **Cut-over**: flipping the default to `ARCH=x86_64` is cheap and reversible; **deleting** `arch/x86`
  is deferred — the i686 reference is the differential-debugging oracle that found most of the MD
  bugs, and it costs nothing to keep unbuilt.

**Key files:** `arch/x86_64/arch.mk`, `arch/x86_64/linker.ld`, `arch/x86_64/boot/{loader.S,
entry64.cpp, bootinfo_x86_64.cpp}`, `arch/x86_64/mm/{Paging.h, AddressSpace.*, mmu_x86_64.cpp}`,
`arch/x86_64/cpu/{cpu_x86_64.cpp, Gdt64.*, Idt64.*, isr64.S, irq64.S, lapic_x86_64.*,
syscall_x86_64.cpp, syscall_entry64.S, switch64.S}`, `arch/x86_64/drivers/{xhci_x86_64.cpp,
