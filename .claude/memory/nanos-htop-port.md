htop 3.5.1 runs on NanOS x86_64 (`make ARCH=x86_64 htop` → `/nanos/bin/htop`). Done on worktree branch `htop-port` off `develop`. Same SDK flow as [[nanos-sdk-and-vim-port]]/[[nanos-networking-stack]]: nanos-port driver + `nxport.toml` at `~/Projects/nanos-sdk-work/htop-port/` (source in `src/`), links the existing x86_64 ncurses (`libncurses.a`/`libtinfo.a`). x86_64-only target (mirrors `make vim`); `make image64` installs it, never depends on it.

**Port mechanics (hooks/pre_configure.sh):** htop's configure picks the platform from `$host_os`; `nanos` is unknown → falls to the do-nothing "unsupported" backend. Hook widens the `linux*|gnu*)` arm of configure.ac to `|nanos*` (NanOS has a real Linux /proc), then `autoreconf -fi`. autoreconf reinstalls the container's config.sub/config.guess (no `nanos`) so the hook re-copies `$SDK/port/{config.sub,config.guess}` afterward. Also strips `AM_LDFLAGS += -rdynamic` (NanOS gcc rejects it). Configure flags: `--disable-unicode` (libncurses, not w), `--disable-sensors/hwloc/capabilities/delayacct/affinity`. Build env: `CFLAGS=-O2 -fno-pie -mcmodel=small -mno-red-zone -include nx-dllimport.h -include nx-getopt-import.h`, `LIBS=-lncurses -ltinfo`.

**libc-glue additions (user/libc-glue, all committed):**
- `posixstubs.c`: `getpriority`/`setpriority` (no nice → 0/no-op), `syscall()` (→ -ENOSYS; htop's uid-gated capget probe never runs at root), `dlopen/dlsym/dlclose/dlerror` (no .so loading → SystemdMeter degrades), and a real `realpath()` (lexical canonicalize + stat existence check; picolibc lacks it → undefined call faulted at rip=0 under ignore-all linking).
- new headers `include/{syscall.h,dlfcn.h,linux/capability.h}` (compat shims for the always-compiled capget probe) + `include/nx-getopt-import.h` (routes optarg/optind/opterr/optopt through libc.ndl `__imp_` slots; scoped -include, NOT global, so bundled-getopt ports are unaffected).
- pairs with nanos-sdk `sysroot/posix-hosted-patch.sh` adding getpriority/setpriority/PRIO_* to `<sys/resource.h>` (UNCOMMITTED in the nanos-sdk repo — commit there for reproducibility).

**/proc work (fs/SynthFs.cpp, kernel/Process.{h,cpp}, host-tested):** htop's Linux backend needed far more than NanOS exposed. Added: ProcInfo `memKb` (brk-heap proxy, no real RSS) + `nthreads`; `/proc/<pid>/statm`; real vsize/rss + num_threads in stat; Uid/Gid/VmSize/VmRSS/Threads in status; MemAvailable/Buffers/Cached/Swap in meminfo. **Two non-obvious blockers (debugged via a /rsp fault-handler print + a standalone openat/fdopendir/fstat proctest.nxe):** (1) `/proc/<pid>/stat` must carry through **field 39 (processor)** — htop's parser bails on a missing field; emit the full 52-field Linux line. (2) htop reads the main thread via **`/proc/<pid>/task/<pid>/stat`** (scanMainThread default true), so SynthFs `classifyProc` now handles the `task/<tid>` level (collapsed onto the tid; main thread tid==pid) + readdir lists the task dir + a `task` entry under /proc/<pid>. Without these the list was silently empty.

**Verified in QEMU x86_64:** boots → shell → `htop` shows all live processes (htop/init.nxe/idle/ksoftirqd-net/net-timer/nsh) with PID/USER/PRI/NI/VIRT/RES/S/CPU%/MEM%/TIME+/Command + working CPU/Mem(171M/512M)/Load/Uptime meters; `q` quits clean. `htop --version` prints 3.5.1.

**Display fixes (feat/smp session, 2026-06-24) — htop looked wrong: 1 CPU, monochrome, no uptime:**
- **1 CPU → 4:** htop counts cores from `/sys/devices/system/cpu/cpuN` (sysfs), NOT /proc/stat. NanOS had no sysfs. Added a minimal one in `fs/SynthFs` (`/sys/devices/system/cpu` skeleton in ctor + `populateSysCpu(smpCpuCount())` called from `kernel/Kernel.cpp` AFTER `smpInit()`, since the count isn't valid at SynthFs ctor time). Also made `/proc/stat` per-core (`cpu0..cpuN`, per-CPU jiffies via `ProcTable::cpuTimesFor`, accountTick charges `arch::smpThisCpu()` slot) + `/proc/cpuinfo` one entry per core.
- **No COLOR (the deep one):** NanOS ncurses is non-widec → terminfo numbers are 16-bit `short`. xterm-256color's `pairs#65536` overflowed `short` → `max_pairs=0` → `start_color()` SKIPS color setup (needs max_pairs>0) and leaves `COLORS=0` → htop falls to COLORSCHEME_MONOCHROME. (has_colors() was actually TRUE — the trap.) Diagnosed by building an in-guest ncurses probe (`~/Projects/nanos-sdk-work/ncprobe-port`, a `build="make"` nanos-port linking -lncurses -ltinfo, `-include nx-dllimport.h` for the stdout/stderr data imports). **Fix:** `ncurses-port/hooks/pre_configure.sh` caps `pairs#0x10000`→`pairs#0x100` in `misc/terminfo.src` (what `--with-fallbacks` bakes from). `--enable-ext-colors` would be the "proper" widen-to-int fix but REQUIRES `--enable-widec` (full wide-char ABI + relink htop widec) — too invasive. Reproduce: `make ARCH=x86_64 ncurses && make ARCH=x86_64 htop && make image64`. Verified: probe COLORS=256/COLOR_PAIRS=256, htop emits 93 color SGR codes, screenshot confirms.
- **Uptime (unknown):** `/proc/uptime` emitted a human string `"uptime: 5 s (...)"`; fixed `uptimeString` to the Linux numeric format `"<secs>.<cc> <idle>.<cc>\n"` (idle = summed across CPUs). All host-tested.
- **Meter misalignment / stale-% / 400%-CPU / huge-TIME+ — ALL one root cause: the VT engine missing editing escapes.** `user/term/vt.c` (the SHARED engine: kernel FbConsole compiles it as `vtk.o`, nterm/nwterm link `bin/vt.o`) only handled `H/f A/B/C/D G/d J K m r s/u h/l`. But xterm-256color terminfo advertises — and ncurses USES for optimized redraws — **REP (`CSI n b`, repeat last glyph)** + ICH(`@`)/DCH(`P`)/ECH(`X`)/IL(`L`)/DL(`M`). REP was the big one: htop fills a meter bar by printing one char + `\E[65b`; unhandled → the 65-char run collapsed to 1, cursor desynced → narrow meter + stale leftover `%` + misread CPU%/TIME+ columns. **Fix:** implemented all six in vt.c (+ a `last` glyph field in vt.h for REP); host-tested in test_vt.cpp (6 cases). After it: meters full-width, bars fill, htop self-CPU sane (~27%), TIME+ sane. Benefits EVERY ncurses app (vim too). Debug method: capture htop's serial output → reconstruct the screen grid with a Python ANSI decoder → tally CSI finals (`b` and `t` were unhandled; `t`=window-ops, safely ignored). NOTE the decoder itself must implement REP or it shows phantom glitches.

**Known cosmetic leftovers (not htop-specific):** stray `B` glyphs before coloured cells = the pre-existing ncurses-nanos `tparm` `%{}`/`%<`/`%t` conditional-cap bug (same class as the [[nanos-sdk-and-vim-port]] SGR follow-up, affects any colour ncurses app). htop can't save its rc (`~/.config/htop` dir not auto-created; non-recursive mkdir). Per-process MEM is the brk proxy (0 for procs that haven't grown the heap); NanOS has no full RSS accounting.
