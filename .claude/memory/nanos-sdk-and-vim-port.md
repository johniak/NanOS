The `nanos-sdk` (public GitHub repo `~/Projects/nanos-sdk`, separate from NanOS) is a real native cross toolchain with triplet **i686-nanos** (patched binutils 2.43 + gcc 14.2 + picolibc), a `nanos-port` driver + `nxport.toml`, and `sync-sysroot`. Ports are GitHub forks (like bash). Build artifacts persist in `~/Projects/nanos-sdk-work` (toolchain is aarch64-Linux, runs only in a container — use image `nanos-sdk-dev` = debian + build deps, bind-mount the work dir at `/work`, `PATH=/work/toolchain/bin:...`).

**Proven end-to-end:** the SDK builds **GNU vim 9.1** into a NanOS `.nxe` with zero manual flags; `vim --version` runs fully on NanOS, and trivial+medium C programs (printf/malloc/qsort/recursion/strdup) run clean. vim **writes to the ext4 disk** (real 4 KiB swap files, e2fsck stays clean) — the [[nanos-ext-readwrite]] write path works from a real port.

**Key SDK mechanism — `sysroot/posix-hosted-patch.sh`** (run by sync-sysroot): picolibc i686-elf gates POSIX behind `__CYGWIN__/__rtems__/__SPU__` not `__POSIX_VISIBLE`, so it patches the *copied* sysroot headers to treat `__nanos__` as hosted — WITHOUT inheriting rtems/cygwin struct layouts (would break the libc.ndl ABI): stat.h lstat/mknod+UTIME, features.h `_POSIX_TIMERS`→nanosleep/clock_gettime, signal.h SA_ONSTACK/SA_RESTART as no-op flag bits, utime.h utime(), resource.h getrlimit/RLIMIT_*. Data symbols (stdout/errno/environ) resolve via the MinGW-style auto-import already in mknx. NanOS libc-glue gained the matching wrappers (commit edca052: rmdir/fsync/sync/fchdir/ftruncate/utime/getrlimit/setrlimit/sigaltstack/execvp/mkdtemp).

**Kernel bug found+fixed (commit d9b2893):** `STAGE_CAP` in kernel/Exec.cpp was 1 MiB but the loader reads the whole .nxe (image+tables) into that window at 0x400000 before copying — any program >1 MiB (vim ~1.6 MiB) overran it, tables fell past the loader's bounds, and it faulted in ring 3 before main. Raised to 4 MiB + reserved the frames (mmu_x86 markRangeUsed) + reject oversize before read. All in-tree apps were <1 MiB so never hit it.

**Interactive vim NOW RENDERS** (welcome screen, `~`, help text, status line) — done by making the kernel framebuffer console a full terminal: `FbConsole` (drivers/FbConsole.*) feeds the shared `vt.c` engine (commit fa31618) and rasterizes its cell grid with a per-cell shadow (repaint = O(changed cells), or boot crawls). The boot console is FbConsole (GRUB gives a 1024x768 fb via the multiboot VIDEO flag); its old parser only did SGR. vt.c gained OSC / `< = >` private CSI markers / CSI intermediates; vt.h is now `extern "C"` and the kernel builds it as `vtk.o`. Shell + pipes + colours all render cleanly.

**vim EDITS AND SAVES to ext4** — verified end-to-end: opened /disks/main/done.txt, inserted text, `:wq`, and the file held the exact content with **e2fsck clean**. This needed a real bug fix: the PS/2 keymap (kernel/KeyDecoder.cpp) left scancode 0x01 (ESC) as `0`, so the ESC key produced no byte and vim could never leave insert mode — now mapped to 0x1b in both tables (commit 97120ed). (Earlier e2fsck "errors" were from repeatedly hard-killing QEMU mid-write across crash tests, not a live bug — a fresh `make image` + clean session is clean.)

**Kernel crashes under heavy interactive I/O — mostly fixed:** (1) FIXED (96fea8c) `SYS_close` woke a pipe's WaitQueue after `close()` freed the Pipe. (2) FIXED-ish (97120ed) a heap-corruption fault surfacing as a wild pointer in `wakeAll` then `Heap::blkUsed`/`setBlk`: grew the per-task kernel stack 8→16 KiB (stacks are heap-allocated, so an overflow scribbles the adjacent heap block) and added a bounds/loop guard to `wakeAll`'s walk (corrupt queue → no-op, not a fault). After this vim edits+saves cleanly. (3) REMAINING — a *rare intermittent* heap corruption can still fault under stress; the garbage is data-like (not stack-frame addresses), so it looks like a data-buffer overflow into the heap, NOT pure stack overflow — ruled out FbConsole/vt bounds, dup/fork refcounts, BlockCache size (MAX_BLOCK 4096 ≥ disk block). Needs dedicated heap instrumentation / a guard-page allocator to pin down. Pipe lifecycle (open/dup/fork/close refcounts) is correct.

**Second SDK port: bzip2 1.0.8** builds cleanly (plain Makefile, no gnulib) and round-trips on NanOS (compress + `bzip2 -d` = exact input); installs to /nanos/bin (Makefile `_image`, optional).

**Shortcut cleanup pass (the user asked to fix all the hacks properly):**
- HEAP CORRUPTION root-caused (commit 54d2d70): it was a kernel-STACK overflow, not a heap bug. The ext write + JBD2 path nests several extent helpers each holding `char buf[4096]`; a few levels + a keyboard IRQ overran the 8/16 KiB heap-allocated kernel stack and scribbled the adjacent heap block. Found it by adding allocator instrumentation to mm/Heap.* — footer-mirrors-header boundary tags, a CANARY red-zone after every allocation, free-list-link + free-head range checks, all validated on alloc/free/realloc and reported via a panic hook (memory_manager.cpp) that prints the block + halts. The panic fired with stack content (0xffffffff + a heap pointer) in a block tag — diagnostic of a stack overflow. Fix: 32 KiB kernel stacks (Scheduler.cpp KSTACK_SIZE); the canary stays as a permanent net. Real follow-up: take the 4 KiB block buffers off the kernel stack.
- The vim SGR `6}38;5;Nm` leak was vim's minimal tgoto() (can't parse terminfo `%{n}%<%t` conditionals), NOT libtinfo tparm — fixed with the simple `setaf=\E[3%p1%dm` terminfo that vim's term_color() expands itself (commit a8426bf). Same commit: Exec.cpp counts argv/envp instead of a hard-coded length (the literal had dropped env vars past the 2nd — why VIMRUNTIME/VIMINIT first didn't reach the shell).
- SDK ignore-all/autoconf fix (toolchain/conftest-strict-wrapper.sh): i686-nanos-gcc is now a wrapper that links autoconf's `conftest` with `--unresolved-symbols=report-all` (wins as the last flag) so AC_CHECK_FUNC reflects real libc.ndl exports, while real builds keep ignore-all for the data auto-import. Plus DT_* dirent constants in the sysroot. This unblocks gnulib-heavy ports (grep) — they were drowning in false HAVE_<fn>=1.

**vim startup polish (commits 497699d, af95675) — a normal `vim <file>` is now clean:**
(1) FULL HEIGHT — the console answered TIOCGWINSZ with -EINVAL so vim used terminfo's 80x24 and painted only the top half; added `arch::consoleSize` (FbConsole grid) + a dispatch TIOCGWINSZ case → vim uses the whole 128x48 screen. (2) NO E1187 — set `$VIMINIT` in the PID1 baseline env (kernel/Exec.cpp); when set, vim runs it as the vimrc and never sources `$VIMRUNTIME/defaults.vim` (vim ignores the env $VIMRUNTIME for its internal runtime path, so shipping defaults.vim alone did NOT help). NOTE: the baseline env count in `archLoadUser(..., envp, N)` is hard-coded — bump N when adding env vars (was silently dropping the 3rd+). (3) NO SGR GARBAGE (`6}38;5;Nm`) — root cause is our libtinfo `tparm` mis-evaluating terminfo's conditional `setaf=\E[%?%p1%{8}%<%t...` arithmetic; the Makefile now recompiles the shipped xterm-256color with the DIRECT `setaf=\E[38;5;%p1%dm`/`setab` (only `%p1%d`, which tparm handles), so vim emits clean colour escapes (the ~ render blue). The real `tparm` `%{}`/`%<`/`%t` bug in ncurses-nanos remains a follow-up affecting any conditional cap.

**libc-glue additions for GNU/gnulib ports:** getprogname/setprogname (seeded from argv[0] by a new crt0 `__nx_set_progname` hook), __fpending (returns 0). SDK `posix-hosted-patch.sh` ships their decls + `<stdio_ext.h>`.

**grep port DONE (GNU grep 3.11 runs on NanOS).** Real regex engine + `-n`/flags verified headlessly (`grep -n p.e` → correct lines+numbers, clean exit). Installs as /nanos/bin/grep (Makefile `make grep` stages bin/grep.nxe from the SDK work dir, `_image` writes it; optional like bash/vim/bzip2). The SDK `ignore-all`/autoconf shortcut is fixed PROPERLY (commit in nanos-sdk: 6ec57af):
- **Honest conftest links** (`toolchain/conftest-strict-wrapper.sh`, installed AS i686-nanos-gcc by sync-sysroot, real driver → `i686-nanos-gcc.real`): autoconf's `conftest` links get `--unresolved-symbols=report-all` (last flag wins) so an absent function is a hard error → no false `HAVE_<fn>=1`; real program links keep ignore-all for data auto-import.
- **Data stub** (`toolchain/gen-conftest-stubs.sh`, run by sync-sysroot): report-all alone is too strict — probes like gnulib's `__fpending` reference the libc DATA symbol `stdin` (left undefined for mknx). The stub WEAKLY defines exactly the pure-data exports (names with an `__imp_` slot in libc.a but no strong def — 129 of them: stdin/stdout/stderr/errno/environ/optarg/locale+iconv tables), so a conftest resolves a symbol IFF libc provides it. Both idempotent, wired into `sysroot/sync-sysroot`.
- **flockfile**: `posix-hosted-patch.sh` now declares flockfile/funlockfile/ftrylockfile + getc_unlocked family as no-ops in sysroot stdio.h (single-threaded stdio → locking is a genuine no-op), making the `_POSIX_THREAD_SAFE_FUNCTIONS` that features.h advertises truthful.
- gnulib's `inet_pton`/socket self-tests live only in `gnulib-tests/` (the bundled testsuite, needs sockets NanOS lacks); building the program is `make -C lib && make -C src` — standard for cross-compiling to a minimal target, not a shortcut. Cache: honest `ac_cv_type_socklen_t=no` (NanOS has no sockets) → gnulib's sys/socket.h `typedef int socklen_t`.

**mknx kernel-side fix (NanOS commit 91a54f9):** mknx wrote the NxNeeded table only from explicit `--need` flags. grep.nxe imports 358 symbols from libc.ndl but was mknx'd without `--need libc.ndl` → empty needed list → loader never loads libc.ndl → every import resolves to 0 → exec fails `-ENOENT` (`NxeLoader.cpp:74`, surfaced to bash as "No such file or directory"). Now mknx DERIVES needed from each import's source-library tag (`.nxlib.<lib>` section), so a module can't import from a lib it doesn't declare needed; explicit `--need` still works, deduped. In-tree .nxe builds unaffected (already pass --need, deduped).

Minor cosmetic leftovers (unchanged): vim 256-colour SGR fragment on coloured help tags; vim runtime E1187 handled via $VIMINIT. See [[nanos-terminal-and-deferred-scheduler]], [[nanos-bash-port]].
